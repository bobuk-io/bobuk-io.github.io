# Как обновлять лендинг

Лендинг — публичный каталог нативных приложений `bobuk-io`: https://bobuk.io/, репозиторий `bobuk-io/bobuk-io.github.io`. Копия на https://bobuk-io.github.io/ собирается из того же репозитория. Здесь собраны правила: когда сайт нужно обновлять, что именно менять и как публиковать. Запуск и деплой описаны в [README](../README.md).

## Когда обновлять

Обновляйте сайт в той же задаче, что и само приложение, не дожидаясь отдельной просьбы, если:

- **приложение стало публичным** — добавьте его страницу на всех трёх языках, иконку, скриншоты и запись в каталоге (раздел «Новое приложение»);
- **релиз меняет то, что видит пользователь** — функции, требования, поддерживаемые системы, разрешения, установку или обновление, данные и privacy, поддержку, удаление;
- **на странице приложения уже объявляются релизы** (Splash Finish, Ting) — добавьте новый релиз;
- **заметно изменился интерфейс** на текущих скриншотах — переснимите их;
- **приложение переименовали, сделали приватным или архивировали** (раздел «Переименование, приватность, архив»).

Не нужно обновлять сайт ради внутренних изменений, о которых он не пишет. Перед решением прочитайте текущий текст страницы приложения. В отчёте о задаче прямо напишите, что лендинг не потребовал изменений.

## Общие правила

- **Факты — из README и release notes приложения.** Сайт не обещает больше, чем написано там. Если README и сайт расходятся, исправьте сайт (или README, если ошибка в нём).
- **Три языка всегда.** Каждое изменение текста делается сразу на en, ru и uk. Ни один язык не остаётся позади. Термины: ru «ведущая клавиша», uk «початкова клавіша», «инбокс»/«інбокс»; названия пунктов меню и кнопок приложения пишутся так, как они выглядят в интерфейсе.
- **Только публичные репозитории.** Репозиторий лендинга публичный, поэтому приватное приложение не должно появляться даже в исходниках: ни в `catalog.json`, ни в текстах, ни в картинках. `npm run app:new` отказывается работать с приватным репозиторием.
- **Только настоящие скриншоты** релизной версии с демо-данными. Никаких макетов и личных данных (раздел «Скриншоты»).
- **Ссылка на App Store** (`appStoreUrl` в `catalog.json`) — только реальная опубликованная.
- **Без аналитики и сторонних скриптов.** Шрифты системные, изображения локальные.
- **Порядок на главной не задаётся вручную.** Первым идёт приложение с самым свежим опубликованным релизом на GitHub. Дату записывает `npm run sync:github` в `src/data/public-repos.json` (поле `updatedAt`). При равных датах действует порядок в `catalog.json`. Публикуйте релиз приложения на GitHub раньше, чем публикуете лендинг, иначе порядок останется прежним до следующей публикации.

## Где что лежит

| Что | Где |
| --- | --- |
| Список приложений: slug, репозиторий, имя, иконка, превью, «Работает с» | `src/data/catalog.json` |
| Тексты приложения на трёх языках, включая подписи к скриншотам | `src/data/apps/<slug>.ts` (тип `AppCopy` в `src/data/types.ts`) |
| Общий интерфейс сайта (меню, кнопки, требования `macOS 14+ · Apple silicon and Intel`) | `src/i18n.ts` |
| Иконки и превью для соцсетей | `public/images/<slug>-icon.png`, `public/images/<slug>.png` |
| Скриншоты | `public/images/shots/<slug>/*.webp` |
| Публичные репозитории и даты релизов (генерируется, руками не правится) | `src/data/public-repos.json` |
| Страница-руководство приложения (необязательно, например «Micro-apps» у Ting): тексты на трёх языках, примеры кода | `src/data/guides/<slug>.ts`, поле `guide` в `AppCopy`; страница `apps/<slug>/<guide.slug>/` |
| Проверки | `scripts/site.test.mjs` |

Slug — постоянный адрес `/apps/<slug>/`, его нельзя менять после публикации. Строка требований в `src/i18n.ts` общая для всех приложений. Если у нового приложения другие требования, не правьте её, а сначала добавьте отдельное поле приложения.

## Релиз существующего приложения

1. Прочитайте release notes и изменения README. Решите, что из этого видит пользователь.
2. Обновите `src/data/apps/<slug>.ts` на трёх языках:
   - **объявление релиза** — как это уже принято у приложения: у Ting первый пункт `features` вида «Ting 0.3.3: …» и раздел на странице поддержки; у Splash Finish вопрос «What’s new in 0.3.12?» первым в `faq`;
   - руководство (`src/data/guides/<slug>.ts`), если оно есть и релиз меняет описанное в нём;
   - функции, требования, установка, обновление, поддержка, privacy, удаление — если релиз их меняет;
   - скриншоты — если интерфейс на них заметно изменился (раздел «Скриншоты»).
3. Обновите или добавьте проверку релиза в `scripts/site.test.mjs` по образцу существующих (`Splash Finish 0.3.12 documents Rex setup…`, `Ting documents release…`): ключевые факты нового релиза должны быть на всех трёх языках.
4. Опубликуйте (раздел «Публикация»). Сообщение коммита: `docs(<slug>): announce <версия> <суть>`, например `docs(ting): announce 0.3.3 quieter ting`.

### Фид обновлений Ting

Начиная с версии после 0.6.1, Ting проверяет обновления по адресу `https://bobuk.io/apps/ting/appcast.xml`. Это файл `public/apps/ting/appcast.xml` этого репозитория. Сами архивы лежат в GitHub Releases, и фид ссылается на них.

- `Scripts/publish.sh` в репозитории Ting сначала публикует релиз на GitHub (вместе с `appcast.xml` для Ting 0.6.1 и старше), а потом копирует `dist/appcast.xml` сюда. Опубликуйте сайт сразу после этого: пока сайт не выложен, установленные копии не видят новую версию.
- Не правьте `appcast.xml` руками: он подписан ключом Sparkle вместе с архивом. Копируйте только файл из `dist/` релиза, уже опубликованного на GitHub.
- Файл должен быть в репозитории: `npm run deploy` делает `rsync --delete`, и файл, положенный на сервер отдельно, удалится. Проверка `Ting update feed…` в `scripts/site.test.mjs` следит, что фид на месте и ссылается на подписанные архивы GitHub.
- После деплоя проверьте, что `https://bobuk.io/apps/ting/appcast.xml` отвечает HTTP 200 с новой версией.

## Новое приложение

Репозиторий уже должен быть публичным в организации `bobuk-io`, не форком и не архивом.

```sh
npm run app:new -- <репозиторий> [--slug <slug>] [--name "<Имя>"] [--icon <png>] [--companions "Home Assistant, Rex"] [--dry-run]
```

Скрипт анонимно проверяет через GitHub API, что репозиторий публичный и принадлежит `bobuk-io`, и что slug и репозиторий ещё не заняты. Затем он:

- создаёт `src/data/apps/<slug>.ts` с заготовкой текстов на трёх языках;
- добавляет приложение в конец `src/data/catalog.json`;
- кладёт иконку 256 px в `public/images/<slug>-icon.png` (берёт `--icon` или ищет `Assets/AppIcon…` в соседнем каталоге приложения);
- создаёт папку для скриншотов и обновляет `public-repos.json`.

`--dry-run` только показывает, что будет сделано. Имя репозитория пишется с учётом регистра (`HAScS`). Slug по умолчанию — имя репозитория в нижнем регистре.

Все видимые тексты в заготовке — метки `TODO(landing)`, а список `shots` пуст. Пока не заполнено всё, `npm test` падает: проверки требуют минимум три скриншота у каждого приложения и запрещают `TODO(landing)` на страницах. Так недописанная страница не попадёт на сайт.

Дальше:

1. Напишите тексты на en, ru и uk по README и release notes: категория, слоган, описание, четыре функции, установка, FAQ, поддержка (диагностика, как безопасно сообщить о проблеме, удаление), privacy (что хранится на Mac, какие сетевые запросы, как удалить данные). Образцы — `src/data/apps/hascs.ts` и `src/data/apps/ting.ts`.
2. Сделайте не меньше трёх скриншотов (раздел «Скриншоты») и вставьте их в `shots` для каждого языка.
3. Проверьте в `catalog.json` поле `companions` («Работает с» на главной) и `platform`.
4. Опубликуйте. Сообщение коммита: `feat(<slug>): add <Имя> to the catalog`.

## Скриншоты

**Правила**

- Это настоящие окна **релизной** версии приложения. Макеты, отрисовки и прототипы не подходят.
- **Демо-данные, а не личные.** В кадре не должно быть личных приложений, путей с именем пользователя, имён, адресов серверов, сообщений, сцен, токенов. Просмотрите каждый кадр перед публикацией.
- Не меньше **трёх** кадров на приложение: главный экран, ключевая функция, настройки или вариант темы.
- Если интерфейс приложения локализован (как у HAScS), снимайте его на языке каждой страницы: файлы `<имя>-en.webp`, `<имя>-ru.webp`, `<имя>-uk.webp`. Английский интерфейс (Splash Finish, Ting) показывается во всех языках.
- У каждого кадра на каждом языке есть короткая подпись (`caption`) и подробное описание для незрячих (`alt`). Подписи не обещают больше README: например, HAScS подтверждает отправку запроса, а не результат на устройствах.
- Формат — lossless WebP без системной тени окна. Тень добавляет сайт.

**Как снимать, не трогая личные данные**

1. Соберите временную копию из исходников релиза в отдельном каталоге (не в репозитории приложения): `git archive <тег релиза> | tar -x -C <каталог>`.
2. В копии:
   - задайте другой bundle ID (`BUNDLE_ID=<id>.screenshots` в `Scripts/package_app.sh`), чтобы настройки и Keychain не пересекались с установленным приложением;
   - уберите из `Info.plist` `CFBundleURLTypes`, иначе копия перехватит ссылки вроде `splash-finish://` или `hascs://` у настоящего приложения;
   - уберите Sparkle-фид (`SUFeedURL`) и регистрацию глобальных горячих клавиш;
   - добавьте небольшой хук по переменной окружения, который после запуска сам открывает нужную панель. Эмулировать нажатия клавиш нельзя без права Accessibility.
3. Изолируйте данные:
   - Splash Finish — `SPLASH_FINISH_HOME=<пустой каталог>`, демо-события через `model.receive(...)` в хуке. Бинарник работает и как CLI: аргументы командной строки ему не передавайте, светлую тему задайте через `defaults write <bundle ID копии> appTheme light`;
   - Ting — `TING_CONFIG=<демо-конфиг>`: в нём все настройки, бинды и история launcha. На клавишах видна вторая буква активной раскладки (это функция). Для launcha выбирайте запрос, который находит только системные приложения (например, «system»): иначе в выдаче окажутся ваши программы;
   - HAScS — в хуке подставной `HTTPTransport` с демо-сценами и `CredentialStorage` в памяти вместо Keychain. Язык интерфейса — аргумент `-AppleLanguages "(ru)"`.
4. Запустите бинарник копии напрямую (`<App>.app/Contents/MacOS/<App>`) с нужными переменными и снимите окна:

   ```sh
   swift scripts/capture-windows.swift <pid или имя процесса> <префикс>
   ```

   Утилите нужно право Screen Recording для терминала. Окна снимаются без системной тени. Первый запуск свежесобранной копии бывает медленным: если окно не попало в кадр, повторите. На Retina-экране кадры получаются вдвое чётче.
5. Превратите снимки в файлы сайта:

   ```sh
   npm run app:shots -- <slug> [--locale ru] [--tight] <снимок.png…>
   ```

   Скрипт обрезает прозрачные поля (`--tight` дополнительно срезает тень, которую рисует само окно, как у панелей Ting) и сохраняет `public/images/shots/<slug>/<имя>.webp`. Затем он печатает записи для `shots` с размерами. Первый снимок нового приложения становится превью для соцсетей.
6. Уберите следы копии: `lsregister -u <путь к копии>.app` (утилита лежит в `/System/Library/Frameworks/CoreServices.framework/Frameworks/LaunchServices.framework/Support/`), `defaults delete <bundle ID копии>` и файл `~/Library/Preferences/<bundle ID копии>.plist`.

## Переименование, приватность, архив

- **Новое название приложения:** поменяйте `name` в `catalog.json` и тексты. Slug не меняйте: это постоянный адрес. Смена slug — отдельная задача: нужен редирект со старого адреса на bobuk.io и редирект-страница в копии на GitHub Pages.
- **Переименован репозиторий:** сразу обновите `repoName` и `repo` в `catalog.json`. Иначе после ближайшего `sync:github` приложение пропадёт с сайта, потому что старого имени больше нет среди публичных репозиториев.
- **Репозиторий стал приватным или архивным:** ближайшая сборка после `sync:github` уберёт его страницы. Для срочного удаления опубликуйте сайт вручную: `npm run deploy`, затем `gh workflow run pages.yml` для копии на GitHub Pages. Если о приложении не должно остаться упоминаний и в исходниках, удалите его запись из `catalog.json`, файл текстов, иконку и скриншоты.

## Публикация

1. Проверки:

   ```sh
   npm run sync:github && npm run build && npm test
   ```

2. Посмотрите изменённые страницы в `npm run preview` на всех трёх языках, на десктопе и на ширине телефона.
3. Закоммитьте и запушьте в `main`.
4. Опубликуйте на bobuk.io: `npm run deploy`. Скрипт ещё раз проверит видимость репозиториев, соберёт и протестирует сайт, скопирует его на oranges.team и проверит главные страницы. Подробности — в разделе «Деплой» в [README](../README.md).
5. Проверьте, что изменённые страницы и новые картинки на https://bobuk.io/ отвечают HTTP 200 и показывают новое содержимое.
6. Push в `main` обновляет и копию на GitHub Pages. Дождитесь её: `gh run watch <id> --exit-status` (id из `gh run list --limit 1`).
